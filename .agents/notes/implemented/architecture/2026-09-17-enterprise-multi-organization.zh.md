# Agent Note: 企业多组织租户机制

Status: implemented

[English](2026-09-17-enterprise-multi-organization.md) | 中文

## Problem

企业登录虽然提供组织字段，但配置的默认组织仍隐式决定 Session 签发、组织列表和 Host 全局管理权限。创建第二个组织不是原子化引导操作，新建受管 Workspace 的文件系统隔间也没有包含组织。若直接把租户管理员当作独立租户管理员，就可能发生同级组织可见、初始化不完整或意外获得 Host 权限。

## Decision

SUNFLECK 将配置的默认组织视为平台组织。只有在该组织内完成认证的管理员才是平台管理员，才可引导创建其他组织，或管理 Host 全局的模型、Credential 与开发检查服务。

组织引导是一次身份仓储事务，同时创建组织、首位已启用管理员、该用户的单向密码校验值和管理员角色；任一步失败都会回滚整个操作。组织编号保持耐久，显示名称可以修改。平台管理员可以列出并修改任意组织名称；租户管理员只能看到并修改本组织，不能创建同级组织。

本地登录在提交的组织内解析用户名，并为同一组织签发浏览器 Session。SSO 沿用已验证的组织映射；若既有外部身份的映射组织发生变化，登录会被拒绝。`/auth/status` 公开当前组织、配置的平台组织、当前主体是否为平台管理员，以及原生登录选择器使用的组织目录。匿名响应只包含组织编号和显示名称；完成认证后，租户只收到本组织，平台管理员收到完整目录。

组织内读写只从认证主体取得 `orgId`。新受管 Workspace 位于 `organizations/<org-hash>/users|departments` 下；既有持久化授权保留原路径。员工、能力、团队、记忆、渠道、Workspace、Session、策略和审计仓储继续执行组织条件。

该边界不会自动隔离外置插件拥有的存储。文档知识插件只有在自己的数据库与 HTTP 操作中携带并校验认证组织后，其内容才适合在同一 Host 的多个租户之间安全使用。

## Alternatives considered

**把每个组织管理员都当作 Host 管理员。** 拒绝采用，因为组织 RBAC 会因此授予模型凭据、运行时配置和同级租户引导权限。租户管理权限继续限定在租户自己的资源内。

**先创建组织，再通过后续请求添加管理员。** 拒绝采用，因为中途失败会留下没有责任管理员、无法使用的组织。单一仓储事务保证引导结果要么完整存在，要么完全不存在。

**把既有 Workspace 授权迁移到新的组织前缀布局。** 拒绝采用，因为持久化路径属于耐久用户数据，立即迁移会增加不必要的部署风险。组织前缀只用于新建 Workspace；既有授权继续按已存路径解析。

**假定插件知识存储会继承核心隔离。** 拒绝采用，因为外置插件拥有自己的 schema 与 HTTP 边界。核心认证无法替代它对自身数据的寻址和授权。

## Consequences

- 相同用户名可以存在于不同组织，并登录为不同主体与 Session。
- 平台管理员可以一次创建可直接登录的租户；租户管理员不能发现或创建同级组织。
- 修改名称只改变治理界面和登录选择器中的标签，不移动 Workspace、Session、用户或其他组织资源。
- 为了让用户选择正确的登录边界，组织编号和显示名称在认证前有意可发现；响应不包含用户、部门、角色或资源。
- Host 全局管理权限明确小于组织管理员角色的适用范围。
- 新受管 Workspace 按组织进行物理隔离，同时保持旧授权兼容。
- 在外置插件自行持久化并校验组织身份之前，文档知识仍是明确的覆盖缺口；该工作交付前，产品不得宣称插件数据已实现租户隔离。
